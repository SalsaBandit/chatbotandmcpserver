# MCP OAuth Technical Briefing

## Executive summary

This solution has two Spring Boot applications:

| Component | Location | Port | Role |
| --- | --- | --- | --- |
| MCP chatbot client | `mcp-client` | `8040` | Browser UI, OAuth client, MCP client, and Ollama chat client |
| Expense MCP server | `mcp-server` | `8060` | OAuth authorization server, OAuth resource server, MCP server, and PostgreSQL-backed expense-tool provider |

The chatbot uses OAuth 2.0 Authorization Code flow with Dynamic Client Registration (DCR). The MCP server dynamically gives the chatbot a client ID and secret. A user authenticates at the MCP server, the MCP server returns an authorization code to the chatbot callback, and the chatbot exchanges that code for tokens. The chatbot then sends the access token only when it invokes the protected `/mcp` endpoint.

This is a proof of concept, not a durable production authorization implementation. Client registrations, connections, authorized clients, user credentials, and issuer-side authorization state are memory/session scoped. Closing the browser session or restarting either application can require authorization again.

## OAuth basics in this application

OAuth lets a user authorize an application to access a protected service without giving that application the user's password.

| Term | Meaning here |
| --- | --- |
| Resource owner | The person who signs in to the Expense MCP server. |
| OAuth client | The chatbot backend. It requests permission to call MCP tools on the user's behalf. |
| Authorization server | The OAuth portion of the Expense MCP server. It authenticates the user and creates codes and tokens. |
| Resource server | The `/mcp/**` portion of the Expense MCP server. It accepts and validates access tokens before serving MCP tools. |
| Client ID and secret | Credentials issued to the chatbot during Dynamic Client Registration. They identify and authenticate the chatbot itself, not the user. |
| Authorization code | A short-lived, one-time value returned to the chatbot callback after the user signs in. It cannot call `/mcp`. |
| Access token | A short-lived bearer credential that authorizes a protected `/mcp` call. In this application it is a signed JWT. |
| Refresh token | A longer-lived credential the chatbot backend can use to request a replacement access token without requiring the user to sign in again. |

### How an access token is generated

1. The chatbot registers with the MCP server and receives a client ID and client secret.
2. The browser redirects the user to the MCP server, where the user signs in. The password stays on the MCP server.
3. The authorization server creates a short-lived, single-use authorization code and redirects the browser to the chatbot callback with that code.
4. The chatbot backend sends the code, matching redirect URI, client ID, and client secret to the MCP server's token endpoint.
5. The authorization server validates the code, redirect URI, and client credentials. If valid, it generates a signed JWT access token and returns it to the chatbot backend, along with a refresh token when applicable.
6. When a tool is needed, the chatbot backend sends only `Authorization: Bearer <access-token>` to `/mcp`. The resource server verifies the JWT signature, issuer, and required authentication before allowing the tool call.

The token is therefore generated by the MCP server's authorization server during the code exchange. The access token is not generated by the browser, the chatbot UI, or the `/mcp` endpoint. The `/mcp` endpoint only validates the token it receives.

## Component responsibilities

### MCP chatbot client (`mcp-client`)

The client hosts the browser UI and accepts:

| Endpoint | Purpose |
| --- | --- |
| `POST /mcp/servers` | Adds an MCP server and starts metadata discovery and DCR |
| `GET /mcp/servers` | Lists MCP connections associated with the current browser session |
| `GET /mcp/servers/{id}/authorize` | Redirects the browser into Spring Security's OAuth authorization-start endpoint |
| `GET /login/oauth2/code/{registrationId}` | OAuth redirect URI; restores the connection to the current session and redirects to the UI |
| `POST /expense` | Sends the user prompt to Ollama with the session's MCP tools available |

Important implementation points:

- `SecurityConfig` installs `McpClientOAuth2Configurer`, which supplies the MCP/OAuth integration.
- `InMemoryMcpClientRegistrationRepository` holds dynamically discovered OAuth client registrations.
- `DefaultOAuth2AuthorizedClientManager` supports `authorization_code` and `refresh_token` grants.
- `DynamicMcpService` constructs an MCP HTTP transport and applies `OAuth2DcrHttpClientTransportCustomizer`. That customizer obtains the authorized client, adds the bearer token to protected MCP calls, and can use the refresh token when necessary.
- The browser UI never receives client secrets, access tokens, refresh tokens, or authorization codes as API data. It only receives connection display data: ID, name, server URL, authorization URL, and whether the connection is currently authorized.

### Expense MCP server (`mcp-server`)

The server performs three roles in one application:

1. **Authorization server:** authenticates the resource owner and issues authorization codes, access tokens, and refresh tokens.
2. **Resource server:** protects `/mcp/**`, validates bearer JWTs, and advertises OAuth protected-resource metadata.
3. **MCP server:** exposes the expense tools and uses PostgreSQL for expense records.

`SecurityConfig` uses three ordered filter chains:

| Order | Protected routes / responsibility |
| --- | --- |
| 1 | OAuth authorization-server endpoints, including authorization, token, JWK, metadata, and OIDC provider configuration |
| 2 | `/mcp/**` and `/.well-known/oauth-protected-resource/**`; validates MCP bearer tokens |
| 3 | Other application routes; permits access and provides form login |

The server advertises itself as the issuer `http://localhost:8060` by default. It exposes the DCR registration endpoint through both authorization-server and OIDC provider metadata as `http://localhost:8060/register`.

## End-to-end OAuth flow

The following assumes the browser is accessing the chatbot at `http://localhost:8040` and connects to the local expense MCP endpoint at `http://localhost:8060/mcp`.

### 1. The user adds an MCP server

The browser UI sends:

```http
POST /mcp/servers
Content-Type: application/json

{
  "name": "Expense MCP Server",
  "serverUrl": "http://localhost:8060/mcp"
}
```

The request also carries the browser's `MCP_CLIENT_SESSION` cookie. The client validates that the MCP URL:

- is an absolute URL;
- contains no query string or fragment;
- uses HTTPS, except that `http://localhost` and `http://127.0.0.1` are allowed for local development.

`DynamicMcpService.add` generates:

- a random connection ID;
- an OAuth registration ID in the form `mcp-<UUID>`;
- a redirect URI based on the incoming chatbot origin, for example:

```text
http://localhost:8040/login/oauth2/code/mcp-<UUID>
```

The client then performs MCP/OAuth metadata discovery. For an MCP server, this includes protected-resource metadata and authorization-server metadata so the client can discover the issuer, authorization endpoint, token endpoint, JWK endpoint, and dynamic registration endpoint. Those discovery calls do not send the user's MCP username or password.

### 2. Dynamic Client Registration (DCR)

The client calls the MCP server's discovered registration endpoint, which is `/register` in this implementation. The application supplies these registration details:

| Field | Value |
| --- | --- |
| `grant_types` | `authorization_code` |
| `redirect_uris` | The generated client callback URI |
| `client_name` | `MCP Chatbot` |

The MCP server validates every redirect URI. It accepts HTTPS redirect URIs, or HTTP only for `localhost` / `127.0.0.1`.

The MCP server generates and returns:

| Returned field | Meaning |
| --- | --- |
| `client_id` | Random UUID identifying this chatbot registration |
| `client_secret` | Random UUID credential for the confidential client |
| `client_id_issued_at` | Registration timestamp |
| `client_secret_expires_at` | `0`, meaning no explicit expiration in this POC |
| `redirect_uris` | The accepted callback URI list |
| `token_endpoint_auth_method` | `client_secret_basic` |
| `grant_types` | `authorization_code`, `refresh_token` |
| `response_types` | `code` |
| `scope` | `mcp.tools` |

The server hashes the client secret with BCrypt before placing it in the `RegisteredClient`; it does not store the raw secret in its `DynamicRegisteredClientRepository`. The client needs the raw secret in its OAuth client registration to authenticate later to the token endpoint with HTTP Basic authentication.

### 3. Browser redirect to authorization

The UI receives an `authorizeUrl` such as:

```text
/mcp/servers/<connection-id>/authorize
```

It redirects the browser there. The chatbot finds the connection in the current HTTP session and redirects again to Spring Security's authorization-start route:

```text
/oauth2/authorization/mcp-<UUID>
```

Spring Security builds the authorization request to the MCP server's discovered authorization endpoint. The standard authorization-code request includes values equivalent to:

| Parameter | Purpose |
| --- | --- |
| `response_type=code` | Requests an authorization code |
| `client_id` | Identifies the dynamically registered chatbot |
| `redirect_uri` | Must exactly match the registered client callback URI |
| `scope=mcp.tools` | Requests access to the MCP tools |
| `state` | Correlates the browser redirect with the authorization request and protects the flow from request forgery |

The exact opaque `state` value is framework generated. It is not an application user ID and must not be logged or modified.

### 4. User authenticates at the MCP server

The browser is now on the MCP server. If no server login session exists, Spring Security redirects HTML requests to `/login`. The user signs in with the configured MCP-server user.

For this POC, that user comes from configuration:

| Configuration | Default |
| --- | --- |
| `MCP_USER_EMAIL` | `demo@example.com` |
| `MCP_USER_PASSWORD` | `password123` |

The password is BCrypt-encoded when the in-memory `UserDetailsService` is created. This is only a demo identity model: it is not backed by the PostgreSQL database and is not suitable for a multi-user production system.

After successful login, the authorization server approves the request without a separate consent screen because the dynamic client sets `requireAuthorizationConsent(false)`. The authorization server redirects the browser to the registered chatbot redirect URI with:

```text
http://localhost:8040/login/oauth2/code/mcp-<UUID>?code=<one-time-code>&state=<state>
```

The authorization code is short-lived and one-time use. It is not an MCP access token and cannot call `/mcp`.

### 5. Code exchange and token storage

The client-side OAuth configuration handles the callback and exchanges the authorization code at the MCP server token endpoint. For the exchange, the chatbot sends:

| Sent to token endpoint | Purpose |
| --- | --- |
| Authorization code | Proves the browser completed authorization |
| Matching redirect URI | Binds the code to the registered callback |
| Client ID and client secret | Authenticates the confidential OAuth client using `client_secret_basic` |
| Authorization-code grant type | Identifies the token flow |

The token response contains an access token and, because the registered client supports it, a refresh token. The client stores the authorized-client record through Spring Security's `OAuth2AuthorizedClientRepository`.

The controller callback also calls `restoreConnection`. That restores the already-created connection into the active browser session by looking it up with its registration ID, then returns the browser to `/`.

### 6. Invoking MCP tools

When the user submits a chatbot prompt, the browser sends the text to `POST /expense`. The chatbot does the following:

1. Reads MCP connections from the current `MCP_CLIENT_SESSION`.
2. Creates an `McpSyncClient` for each connection.
3. Supplies the resulting MCP tool callbacks to Spring AI's `ChatClient`.
4. Sends the prompt and available tool definitions to the configured local Ollama model (`gemma4`).
5. If the model selects an MCP tool, the MCP transport invokes the server's `/mcp` endpoint.

For the protected MCP call, the OAuth transport customizer retrieves the authorized client and sends:

```http
Authorization: Bearer <access-token>
```

The client does **not** send the resource-owner password, client secret, refresh token, authorization code, or browser session cookie to `/mcp`.

The MCP server validates the JWT by:

- obtaining signing keys from `<issuer>/oauth2/jwks`;
- validating the token issuer against `mcp.oauth.issuer-uri`;
- requiring authentication for `/mcp/**`.

The resource configuration currently sets `validateAudienceClaim(false)`, so it does not enforce an `aud` claim. The advertised MCP scope is `mcp.tools`.

The MCP tool methods use `SecurityContextHolder` to log the JWT subject when a tool is invoked, then perform CRUD/search operations against the PostgreSQL `persons` table.

## What data goes where

### Data sent from the chatbot client to the MCP server

| Stage | Data sent |
| --- | --- |
| Metadata discovery | MCP server URL is used to retrieve public OAuth/MCP metadata |
| DCR | Client name, authorization-code grant type, and callback redirect URI |
| Authorization redirect | Client ID, redirect URI, requested scope, response type, and framework-generated state |
| Token exchange | Authorization code, redirect URI, grant type, and client credentials via HTTP Basic |
| MCP invocation | Bearer access token and the MCP protocol request/tool arguments |

The initial `POST /mcp/servers` browser request sends the descriptive server name and server URL to the chatbot only. Those values are not credentials.

### Data returned by the MCP server to the chatbot client

| Stage | Data returned |
| --- | --- |
| DCR | Client ID, raw client secret, permitted redirects, grants, scope, and authentication method |
| Authorization redirect | One-time authorization code and state |
| Token exchange | Access token, refresh token when issued, token type, expiry, and scope |
| MCP call | Tool definitions and tool result data, including expense-record information requested by the model |

### Data stored by the chatbot client

| Data | Storage in current implementation | Persists after browser session / restart? |
| --- | --- | --- |
| Browser session identifier | Browser cookie named `MCP_CLIENT_SESSION` | Typically no after session end |
| Connection ID, name, MCP URL, registration ID | `HttpSession` attribute in `DynamicMcpService` | No |
| Registration-ID-to-connection lookup | `ConcurrentHashMap` in application memory | No after application restart |
| Dynamic OAuth client registration, including client credential material | `InMemoryMcpClientRegistrationRepository` | No after application restart |
| Access token and refresh token | Spring Security's authorized-client repository, session scoped by default here | No after session end/restart |
| Chat prompt | Processed by the chatbot/Ollama integration; no application database persistence is configured | No application persistence |

The browser is not deliberately given token values. It holds the session cookie, which lets it refer to server-side session state while the session remains valid.

### Data stored by the MCP server

| Data | Storage in current implementation | Persists after restart? |
| --- | --- | --- |
| Demo user name and BCrypt-hashed password | `InMemoryUserDetailsManager` | No |
| Dynamic OAuth client registration | `DynamicRegisteredClientRepository`, two in-memory maps | No |
| Raw client secret | Not retained in the custom repository; BCrypt hash is held in `RegisteredClient` | No |
| OAuth authorization/token service state | No persistent authorization service is explicitly configured; treat as in-memory POC state | No |
| MCP server login session | Servlet session cookie named `MCP_SERVER_SESSION` | No by default |
| Expense records | PostgreSQL `persons` table, managed by JPA | Yes |

## Why authorization is not durable today

The current behavior is expected from the code:

- Connections belong to the browser `HttpSession`.
- The client registration repository is explicitly in memory.
- The registration-ID lookup map is explicitly in memory.
- OAuth authorized clients are session scoped in this setup.
- The server's registered OAuth clients and demo user are in memory.

As a result, closing the browser session loses the client session cookie and its server-side connection/token association. Restarting either application loses its in-memory structures. The user must authorize again.

## Current security posture and POC limitations

### Positive controls present

- Server URLs must use HTTPS except for local loopback development.
- Dynamic redirect URIs are restricted to HTTPS or local loopback HTTP.
- Client secrets are BCrypt-hashed by the MCP server after registration.
- OAuth uses authorization code flow rather than collecting the MCP user password in the chatbot.
- Access and refresh tokens remain server-side in the chatbot rather than being returned to browser JavaScript.
- The resource server validates JWT issuer and obtains keys from the issuer JWK endpoint.
- PostgreSQL password is externalized as `POSTGRES_PASSWORD`, rather than embedded in YAML.

### Limitations to state clearly

| Limitation | Why it matters |
| --- | --- |
| No durable application user identity in the chatbot | There is no stable user key to associate saved authorizations with a real chatbot user |
| Session/in-memory token storage | Reauthorization is required after session loss; not suitable for durable authorization |
| In-memory registered OAuth clients | Server restart invalidates dynamically registered clients |
| Demo credentials have defaults | `demo@example.com` / `password123` must never be used outside local development |
| No consent screen | Users are not shown a scope approval step |
| No audience validation | Resource server accepts a valid issuer token without checking `aud` |
| CSRF disabled in both applications | Convenient for the POC, but should be reviewed before browser-facing production deployment |
| Debug logging enabled for Spring AI | Must be reviewed to ensure prompts, tool inputs, and protocol details are not over-logged |
| No token revocation/disconnect lifecycle | No endpoint currently deletes authorized-client records or revokes tokens |
| `ddl-auto: update` | Convenient for development; production migrations should be explicit and controlled |

## Production direction

To make authorization durable and production ready:

1. Add real chatbot authentication and a stable application user ID.
2. Persist MCP connections, OAuth client registrations, authorized clients, and server-side authorization state in approved durable stores.
3. Encrypt refresh tokens and any required client-secret material at rest; restrict database and key access.
4. Use supported Spring Security persistent authorized-client and authorization-service implementations.
5. Replace the in-memory MCP-server user with an approved identity provider or user store.
6. Add disconnect, token-revocation, expiry, refresh-failure, and reauthorization behavior.
7. Require HTTPS, configure secure cookie attributes, enable appropriate CSRF protection, and enforce token audience validation.
8. Add audit logging that records security events without logging raw tokens, secrets, authorization codes, or sensitive tool data.

## Manager discussion prompts and concise answers

### What OAuth flow is used?

OAuth 2.0 Authorization Code flow, with Dynamic Client Registration. The browser participates only in redirects and MCP-server login; the chatbot backend is the confidential OAuth client that exchanges the code and stores tokens.

### What is the third-party application?

The third-party application is represented by the MCP server. In this local POC, `mcp-server` plays both the OAuth provider and protected API/tool provider. In a real integration, those can be separate systems.

### Does the chatbot receive the MCP user's password?

No. The user enters credentials only on the MCP server's login page. The chatbot receives OAuth artifacts—registration credentials, authorization code through the browser redirect, and tokens through the backend token exchange—not the user password.

### Does the browser receive access or refresh tokens?

Not through this application's JSON APIs. Tokens are stored server-side in the Spring Security authorized-client/session mechanism. The browser has a session cookie.

### What credentials does the chatbot send to the third party?

During DCR it sends client metadata and a redirect URI. During token exchange it sends the one-time authorization code and its client credentials. During MCP calls it sends only the bearer access token.

### What does the MCP server validate for an MCP request?

It requires a bearer JWT on `/mcp/**`, validates its issuer using keys from the server JWK endpoint, and exposes `mcp.tools` as the MCP scope. Audience validation is currently disabled and should be enabled for production.

### Why is reauthorization needed after closing the browser?

The connection and authorized-client/token data are tied to the server-side HTTP session, and the browser session cookie is not durable. The dynamic registration structures are also in-memory.

### What is persisted in PostgreSQL?

Expense records in the `persons` table. OAuth clients, tokens, authorizations, and the demo user are not stored there in the current implementation.
